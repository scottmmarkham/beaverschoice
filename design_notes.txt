Reflection Report

Project Overview
For this project, I built a multi-agent system for handling customer requests for paper supply products. The system accepts a natural-language request, extracts the requested items and quantities, checks inventory, determines whether any items are short or out of stock, generates a quote, records the appropriate transactions, and returns a customer-facing response.

My goal was to design a system that separates responsibilities clearly while still keeping the overall workflow easy to test and debug. Rather than relying entirely on a language model to make business decisions, I used deterministic Python logic for the core workflow and used agent-style decomposition to organize the system into smaller, focused responsibilities.

System Architecture
The system is organized around an orchestrator and several specialized agents/functions:

1. Orchestrator Agent
The orchestrator is the main controller for the workflow. It receives the customer request, calls the parsing logic, routes work to the inventory, quote, and order components, and combines the results into a final response. I used this component to keep the end-to-end flow centralized and readable.

2. Inventory Agent
The inventory component is responsible for checking current stock levels for requested items, identifying shortages, and estimating supplier delivery dates when inventory is insufficient. This part of the system uses the inventory-related helper tools to ground decisions in database data rather than assumptions.

3. Quote Agent
The quote component calculates pricing for requested items and can reference prior quote history for similar requests. Its role is to produce the pricing portion of the workflow while remaining separate from inventory and transaction logic.

4. Order Agent
The order component records transactions in the database. When items are fulfilled from stock, it records the sale transaction. When shortages occur, it records the corresponding stock-order activity needed to satisfy the request.

Why I Chose This Design
I chose a multi-agent structure because the project naturally breaks into distinct business tasks: understanding the request, checking stock, pricing the order, and recording the results. Separating these concerns made the code easier to reason about and easier to improve incrementally.

I also chose to keep the most important business logic deterministic in Python instead of depending entirely on LLM output. This was especially important for request parsing, inventory checks, quantity calculations, and transaction creation. A deterministic approach made the system more reliable, easier to test, and less likely to fail on repeated runs.

Tool and Function Usage
The project starter code provided several helper functions, and I mapped them to the agent responsibilities rather than inventing separate tools unnecessarily.

Inventory-related tools:

Quote-related tools:

This mapping helped keep the implementation aligned with the provided project structure while still reflecting a multi-agent design.

Workflow
The final workflow of the system is:

1. Receive a customer request in natural language.
2. Parse the request into requested items, quantities, and request date.
3. Normalize item names so common singular/plural and alias variations map to supported inventory items.
4. Check inventory for each requested item.
5. Determine whether each item is fully available, partially available, or unavailable.
6. Estimate supplier delivery timing for shortages.
7. Calculate quote totals.
8. Record the relevant transactions in the database.
9. Return a final response summarizing availability, shortages, pricing, and delivery timing.

Key Implementation Decisions
One of the most important parts of the project was improving the request parser. Early versions of the parser were too brittle and failed on realistic customer phrasing. I revised the parsing logic so it could better handle:
- multiple requested items in one sentence
- punctuation such as commas, question marks, and periods
- filler phrases such as “please send,” “I need,” or “I’d like”
- singular and plural item variations
- unsupported items, which should be preserved and reported rather than silently dropped
- duplicate item mentions, which can be merged into a single quantity total

This was an important improvement because the quality of the entire workflow depends on correctly extracting the customer’s request.

Another important design decision was normalizing item names before inventory lookup. This reduced failures caused by small wording differences such as “cup” vs. “cups” or “sticky note” vs. “sticky notes.”

I also updated quote-history search behavior so that searches across multiple terms were more flexible. Using broader matching improved the usefulness of historical quote retrieval.

Challenges and How I Addressed Them
The main challenge in this project was balancing an agent-based design with predictable system behavior. A purely LLM-driven solution would have been simpler to describe conceptually, but it would have been harder to validate and debug. I addressed this by using the agent structure mainly for separation of responsibilities while keeping the actual business logic grounded in Python and database-backed helper functions.

Another challenge was handling natural-language variation in customer requests. Real requests are often messy, and the parser needed several improvements before it could handle more realistic phrasing. I addressed this by making the parsing flow more structured: extract the date first, remove known filler text, split the request into chunks, identify quantity-item pairs, normalize the item names, and preserve unsupported requests for reporting.

Testing and Validation
I tested the system using both targeted parser checks and end-to-end scenarios. My testing focused on:
- supported item requests that are fully in stock
- partially fulfilled requests
- completely out-of-stock requests
- unsupported item requests
- requests with punctuation and conversational phrasing
- alias and singular/plural normalization
- database transaction creation after processing requests

This testing helped reveal weaknesses in parsing and response generation, which led to several refinements in the implementation.

What I Learned
This project reinforced that multi-agent design is most useful when each component has a clear responsibility and a well-defined interface. I also learned that natural-language input handling is often the weakest part of a system unless it is carefully normalized and validated before downstream processing.

A second key lesson was that deterministic logic is often the best choice for business rules, even in an agentic system. The agent pattern helped structure the solution, but reliability came from explicit parsing, normalization, inventory checks, and transaction logic.

Future Improvements
If I continued improving this project, I would:
- expand the parser to support more request formats such as “cups x 10”
- improve the final response formatting to make customer messages more polished
- strengthen automated tests further with more edge cases
- make quote-history usage more intelligent when generating pricing context
- separate quote generation from transaction creation more explicitly if the business process required quotes to be non-binding until accepted

Overall Reflection
Overall, I believe the final design is a practical multi-agent solution that balances modularity with reliability. The orchestrator-and-specialist structure made the workflow easier to understand, while the deterministic implementation choices made the system easier to test and improve. The strongest part of the final solution is the clearer separation of responsibilities combined with more robust request parsing and normalization.
