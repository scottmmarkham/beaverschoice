Design Notes and Reflection

System Overview

This project implements a multi-agent sales support workflow for Beaver's Choice Paper Company. The system receives a customer request, parses the requested items and date, checks inventory, determines whether items can be fulfilled immediately or require restocking, looks up similar historical quotes, records transactions, and produces a customer-facing response.

The architecture uses an orchestrator-style design with supporting worker agents and deterministic business logic. The orchestrator agent is intended to control the workflow by delegating tasks to specialized agents, while Python outside the orchestrator mainly handles request parsing plus light validation and fallback/default handling. This design was chosen to balance flexibility from LLM-based reasoning with reliability for inventory and transaction logic.

Workflow Diagram Explanation

The workflow diagram for this project shows four main components:

1. Request Parser / Normalizer
   - Extracts the request date, item names, and quantities from the incoming customer message.
   - Maps aliases such as “card stock” to canonical item names such as “Cardstock.”
   - Separates supported items from unsupported items.

2. Orchestrator Agent
   - Receives the parsed request.
   - Delegates inventory checks and supplier delivery-date estimation to the inventory agent.
   - Delegates quote-history lookup to the quote agent.
   - Delegates transaction creation to the order agent.
   - Synthesizes the final structured result, including stock status, totals, restocking needs, and the final customer-facing message.

3. Worker Agents
   - Inventory agent: checks stock levels and supplier delivery timing.
   - Quote agent: retrieves similar historical quotes from the quote database.
   - Order agent: records sales transactions and stock-order transactions.

4. Database / Data Layer
   - Stores inventory, quote history, quote requests, and transactions.
   - Provides the source of truth for stock levels, cash balance, and inventory value.

The decision-making process behind this architecture was to separate responsibilities clearly. Inventory lookups, quote lookup, and transaction recording are distinct tasks, so they were assigned to different worker agents. The orchestrator sits above them and is responsible for sequencing those tasks and combining their outputs into one final answer. This makes the system easier to reason about and easier to extend than a single monolithic agent.

Tool and Function Usage

The wrapped tools used by the final implementation are:

- inventory_check_tool
- supplier_delivery_tool
- quote_history_tool
- create_sales_transaction_tool
- create_stock_order_transaction_tool

These tools support the main business tasks of checking stock, estimating supplier timing, referencing prior quote information, recording completed sales, and recording stock replenishment actions.

An important correction is that get_all_inventory is not currently wrapped as an implemented tool in the system. Earlier descriptions overstated the tool coverage by implying that broader inventory retrieval was directly exposed as a wrapped tool. The reflection should therefore focus on the tools that are actually implemented and used in the code.

Why Deterministic Logic Was Used

The system combines LLM-based orchestration with deterministic business logic because some tasks need to be reliable and repeatable. Inventory quantities, transaction creation, and financial calculations are better handled through Python and database functions than through free-form model reasoning. This reduces the chance of hallucinated stock levels or inconsistent totals.

At the same time, the orchestrator prompt was designed so that the orchestrator agent is responsible for workflow control: deciding whether an item is in stock, partially in stock, or out of stock; deciding when to request supplier delivery timing; deciding when to create sales or stock-order transactions; and producing the final structured response.

Evaluation Results from test_results.csv

The generated evaluation file shows that the system demonstrates several clear strengths, but it also reveals important weaknesses.

Strengths observed in the evaluation

1. Successful full fulfilment cases
   Several requests were handled successfully when the parser recognized supported items and the inventory workflow aligned with available stock.

   - Request 4 is a good example. The system confirmed fulfilment of 250 sheets of A4 paper and correctly identified “high-quality paper” as unsupported.
   - Request 9 is another strong case. The system successfully processed 200 units of A4 paper and returned a concise customer-facing response with no restocking needed.
   - Request 10 is also a strong success case. The system fulfilled 500 sheets of Glossy paper and 300 sheets of Cardstock and reported that no restocking or unsupported items were involved.
   - Request 15 shows another successful multi-item fulfilment, where 5 sheets of A4 paper and 500 sheets of colored paper were fulfilled together.

   These examples show that the system can correctly handle supported multi-item requests, calculate totals, and produce a customer-facing fulfilment message when parsing and inventory checks work as intended.

2. Partial fulfilment and restocking behavior
   The evaluation also shows that the system can detect shortages and trigger restocking workflows.

   - Request 8 correctly fulfilled 272 sheets of A4 paper and identified a shortage of 228 sheets, with an estimated delivery date.
   - Request 11 fulfilled 500 sheets of Glossy paper and correctly identified that 28 sheets of A4 paper required restocking.
   - Request 17 fulfilled 272 sheets of A4 paper and identified a much larger shortage of 728 sheets.
   - Request 19 also shows shortage handling, where 272 sheets of A4 paper were fulfilled and 1728 additional sheets were identified as needed.

   These rows demonstrate that the system can distinguish between immediate fulfilment and pending restock, and can communicate both in the final response.

3. Unsupported item handling
   The system also shows evidence of correctly identifying unsupported items.

   - Request 4 correctly flagged “high-quality paper” as unsupported.
   - Request 5 fulfilled supported items while identifying “sheets of 8” as unsupported.
   - Request 6 identified “white printer paper” as unsupported.
   - Request 20 correctly identified “posters” and “tickets” as unsupported while also handling a stock shortage for Flyers.

   These examples show that the parser and normalization logic can separate supported and unsupported requests rather than failing completely.

4. Financial state updates across the run
   The evaluation file shows that cash balance and inventory value changed over time as requests were processed. This demonstrates that transaction creation and financial reporting are connected to the workflow rather than being static outputs. Even though the balances do not change on every row in the current results, the system does update business state during the run and produces a final financial report at the end.

Weaknesses observed in the evaluation

1. Some requests fall back to generic failure responses
   Requests 13 and 14 both returned “We could not fully process your request.” This indicates that the orchestrator output was not always successfully parsed into the expected structured format, or that the request was not handled cleanly enough to produce a final customer-ready answer.

2. Response quality issues in earlier outputs
   One of the major issues identified during iteration was that customer-facing responses could expose too much internal system information. Earlier versions of the system risked leaking internal orchestration-style content such as:
   - orchestrator summaries
   - recognized item structures
   - stock-processing details
   - historical quote data
   - internal pricing breakdowns
   - transaction identifiers

   This is not appropriate for a customer-facing response. The system was later adjusted so that a dedicated customer_message field is used as the only customer-facing summary, while richer orchestration data is kept internal.

3. Inconsistencies in delivery dates and stock messaging
   Some rows in test_results.csv show delivery dates that do not align cleanly with the request date or with the expected supplier timing logic. For example, some responses reference dates in 2023 while the request dates are in 2025. This indicates that the system still has consistency issues in how delivery dates are sourced or surfaced.

4. Parsing and normalization edge cases
   The evaluation also shows that some requests are only partially understood. For example, unusual phrasing or ambiguous item descriptions can lead to unsupported-item classification or incomplete handling. This is especially visible in rows where the response is generic or where the unsupported item wording is awkward.

Reflection on Orchestration Limitations

Although the architecture is described as multi-agent, the current design still has limitations in how fully agent-driven it is.

The intended design is orchestrator-led: the orchestrator should decide delegation, fulfilment status, restocking, transaction creation, totals, and the final customer response. However, in practice, the system still depends on Python for request parsing and for light schema validation/default filling after the orchestrator returns a result. This means the architecture is not a fully autonomous multi-agent system in the strongest sense.

This creates several limitations:

- If the orchestrator returns malformed output, Python fallback logic must repair or replace it.
- The quality of the final result still depends heavily on deterministic post-processing.
- Some inconsistencies can appear between orchestrator-generated summaries and the final validated payload.
- The system is more robust than a fully free-form agent design, but less purely agent-driven than the ideal architecture described in the rubric.

In a future iteration, I would move even more routing, branching, and synthesis responsibility into the orchestrator agent itself. For example, I would require the orchestrator to always return a stricter schema and possibly use structured output enforcement so that less fallback logic is needed in Python.

Design Strengths

The strongest parts of the current design are:

- clear separation of responsibilities between parser, orchestrator, and worker agents
- deterministic handling of inventory and transactions
- ability to handle full fulfilment, partial fulfilment, and unsupported items
- integration with a persistent database for financial state and transaction history
- improved customer-facing response shaping through a dedicated customer_message field

Suggestions for Further Improvement

1. Improve parser robustness
   The parser should be expanded to better handle ambiguous phrasing, unusual units, and descriptive item names. This would reduce the number of generic failures and unsupported-item misclassifications.

2. Enforce stricter orchestrator output structure
   The orchestrator should be constrained more strongly so that it always returns a valid schema. This would reduce fallback cases like Requests 13 and 14 and make the architecture more genuinely orchestrator-led.

3. Improve delivery-date consistency
   The system should use one clear source of truth for supplier delivery dates and ensure those dates always align with the request date and quantity logic.

4. Add stronger response-quality filtering
   A final response-shaping layer could validate that customer-facing output never includes internal fields, transaction IDs, raw stock values, or orchestration/debug text.

Conclusion

This project demonstrates a functional multi-agent workflow for inventory checking, quote support, and order processing. The evaluation results show that the system can successfully fulfil supported requests, detect shortages, trigger restocking, and identify unsupported items. At the same time, the generated results also reveal weaknesses in parsing robustness, delivery-date consistency, and response formatting.

Overall, the current implementation is a solid hybrid design: the orchestrator coordinates the workflow, worker agents perform specialized tasks, and deterministic Python/database logic provides reliability. The next major step would be to make the orchestrator even more central to routing and synthesis while improving parser robustness and customer-response consistency.
